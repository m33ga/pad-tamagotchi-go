# Configuration

The deployment uses one `compose.yaml` and two networks. `internal` carries all
traffic between containers and is declared `internal: true`, so nothing on it can
reach the internet. `edge` is joined only by the seven containers that publish a
port: the gateway, the two Guild chat instances, Service Discovery, which also
needs it to reach the Discord webhook, the message broker, Grafana and Jaeger.
Every container names its networks explicitly.

Only `GATEWAY_PORT`, `GUILD_CHAT_PORT_1` and `GUILD_CHAT_PORT_2` are published to the
network. Service Discovery publishes `127.0.0.1:8500`, the broker's admin endpoints
`127.0.0.1:8501`, Grafana `127.0.0.1:3000` and the Jaeger UI `127.0.0.1:16686`, all
reachable from the host and nowhere else.
Guild's REST listener stays on container port 8081 and its separate socket
listener uses port 8082. Each negotiation returns its serving instance's socket
address, defaulting to localhost and its own published port. Optional
`GUILD_PUBLIC_WS_URL_1` and `GUILD_PUBLIC_WS_URL_2` values override those addresses
for remote clients.

When upgrading an existing `.env`, replace `GUILD_CHAT_PORT` with
`GUILD_CHAT_PORT_1` and `GUILD_CHAT_PORT_2`. Replace a custom
`GUILD_PUBLIC_WS_URL` with the two instance-specific URL overrides above.

## Environment

Copy `.env.example` to `.env` if it does not exist, then replace the database and
cache placeholders. Preserve passwords belonging to existing volumes.
The gateway, Service Discovery and message broker images, `grdz/gateway:4.3.0`,
`grdz/service-discovery:4.1.0` and `grdz/broker:4.5.1`, are pinned directly in
Compose, as are Tamagotchi and Notification, `johnnyc05/pad-tamagotchi-service:v4.2.0`
and `johnnyc05/pad-notification-service:v4.2.0`. All five export traces and metrics to
the [observability stack](../README.md#observability).
`SERVICE_PLATFORM` selects the Tamagotchi and Notification container architecture.
It defaults to `linux/amd64`, which also works through emulation on Apple Silicon.
Set `linux/arm64` when the selected service images provide that architecture.
The other images use their native platform.

Services reach each other through the message broker at `MESSAGE_BROKER_ADDRESS`,
which defaults in code to `broker:9090` and is never set in `.env`. Client requests
use the gateway's published address and the service prefix.
`GATEWAY_URL=http://api-gateway:8080` stays in `.env` only for the services that
still call their peers through the gateway; a service on the broker ignores it.

API containers load shared settings from `.env`. Each client additionally loads
its own `secrets/<client-id>.env`, generated by the setup script, with the generic
credential names expected by that service. Compose `environment` entries are
used only for container addresses, overrides or image-specific variable names.
Only User Management mounts the private signing key; the gateway obtains public
keys through JWKS.

`REQUEST_TIMEOUT_SECONDS` and `MAX_CONCURRENCY` configure service admission and
deadlines. Gateway budgets and upstream timeouts are configured separately in
`config/gateway.yaml`, along with the service prefixes and the public-operation
allowlist.
Every service uses a 4 second request deadline, below the gateway's 5 second
upstream timeout, so a slow request ends with the service's own
`504 REQUEST_TIMEOUT`. The per-service overrides `TAMAGOTCHI_REQUEST_TIMEOUT_SECONDS`
and `NOTIFICATION_REQUEST_TIMEOUT_SECONDS` are no longer read from `.env`. Tamagotchi 4.2.0
validates health statistics against Package Registry over gRPC through the broker, which
Package Registry serves only from its broker release (#97). Until then Compose keeps
Tamagotchi on its built-in registry mock whatever `USE_MOCK_PACKAGE_REGISTRY` says; that
variable still applies to User Management, and Tamagotchi follows it again with that
release.

## Message Broker

The message broker carries every client request, every call between services and
every event. It runs as the `broker` container with two listeners on the internal
network: the gRPC `Broker` API on `9090`, which the gateway and the services call,
and HTTP on `8080`, which serves only `/health`, `/status` and the admin endpoints
`/topics` and `/dead-letters`. Compose publishes the HTTP listener on
`127.0.0.1:8501`, so the admin endpoints can be read from the host and from no other
machine, for example `curl http://127.0.0.1:8501/topics`. They need no token and are
unreachable through the gateway.

Every broker setting defaults in code to its deployment value. Compose sets only
`BROKER_DATABASE_URL`, built from the three `.env` values of its event store:

| Variable | Purpose |
|---|---|
| `BROKER_DB_NAME` | Database of the event store |
| `BROKER_DB_USER` | Its user |
| `BROKER_DB_PASSWORD` | Its password, a secret like the other database passwords |

The event store is the `broker-db` container (`postgres:17-alpine`, internal network
only) with its data in the `broker-db-data` volume. It holds the events queued for
every subscribing service and the dead letter channel, so queued events survive a
restart of the broker or of its database. Requests and replies live only in the
broker's memory and expire with their deadline. The broker starts once Service
Discovery and `broker-db` are healthy, and the gateway once the broker is.

The per-instance circuit breaker and quarantine belong to the broker, so the
gateway's `GATEWAY_INSTANCE_BREAKER` setting no longer exists.

The gateway authenticates its `Send` calls as the `api-gateway` service client, so
that the broker accepts the user identity it passes on. Its credentials come from
`secrets/api-gateway.env`, generated by the setup script like every other client's.

## Service Discovery

Service Discovery needs one secret and nothing else.

| Variable | Default | Purpose |
|---|---|---|
| `DISCORD_WEBHOOK_URL` | empty | Where alerts are posted. Empty means alerts are logged only, with one `alerts_log_only` warning at startup |
| `LOAD_ALERT_THRESHOLD` | `0.8` | Utilization at or above which an instance raises `load_critical`; it recovers below `0.6` |
| `SELF_PRESERVATION` | `off` | Not in `.env.example`. `on` suspends evictions while more than half of a service's instances fail at once; off, a single failing instance is always evicted |

To obtain a webhook URL, open the Discord channel's settings, then
**Integrations > Webhooks > New Webhook**, and copy its URL into your local `.env`.
The URL is a credential: anyone holding it can post to the channel. Never commit
it, paste it into an issue or a pull request, or put it in a Postman environment.
If it leaks, delete the webhook in Discord and create a new one.

`SERVICE_DISCOVERY_URL` does not appear in `.env.example` either. Every service,
the gateway and the broker included, defaults it in code to `http://service-discovery:8080`, the
deployment address, so it exists only as an override.

The registry keeps its state in the `service-discovery-data` volume. There is no
heartbeat: an instance registers once at startup, so a registry that loses that
volume forgets the fleet until every service is restarted.

## Observability

| Variable | Default | Purpose |
|---|---|---|
| `GRAFANA_ADMIN_PASSWORD` | none, required | Password of Grafana's `admin` user, needed to change dashboards or settings. Viewing needs no login |
| `GRAFANA_PORT` | `3000` | Loopback port of Grafana |
| `JAEGER_UI_PORT` | `16686` | Loopback port of the Jaeger UI |

`OTEL_EXPORTER_OTLP_ENDPOINT` does not appear in `.env.example`: every
instrumented service defaults it in code or in its image to
`http://otel-collector:4317`. The collector, Prometheus, Loki and Grafana read
their configuration from `observability/`; see [Observability](../README.md#observability).

Service Discovery 4.1.0 exports registry health/load gauges, lifecycle counters and HTTP
traces to that collector. Its resource is `service.name = service-discovery` and
`service.instance.id = <hostname>`. The metric reader runs every 4 seconds by default;
`OTEL_METRIC_EXPORT_INTERVAL` is an optional positive-millisecond override, and an empty
`OTEL_EXPORTER_OTLP_ENDPOINT` disables export for standalone development. Neither setting
belongs in `.env.example`. The collector is not a readiness or startup dependency: if it is
stopped, Discovery continues probing, serving its API and delivering alerts.

Instance gauges read live registry membership. Deleted instances stop producing samples;
Prometheus keeps their historical data and applies its normal lookback to instant queries.
Request log lines carry `traceId` and `spanId`, so the existing Loki/Jaeger links work.

## Generate Client Credentials

Generate a 32-byte random base64url secret and its SHA-256 hash in one command:

```sh
just gen-client-secret battle-service
# Without just: python3 scripts/generate_client_secret.py battle-service
```

The output labels both destinations:

```text
BATTLE_CLIENT_SECRET=<plaintext>       # local .env; used by the Battle client
BATTLE_CLIENT_SECRET_HASH=<sha256-hex> # local .env; used by the UMS client registry
```

Use the corresponding client ID for each of the eight clients: the seven services
that call others and the gateway, `api-gateway`. Client IDs and allowed scopes are
recorded in `config/service-clients.yaml`. The generator does
not write either value to Git. Keep its output private.

Alternatively, prepare all credentials and the signing key together:

```sh
python3 scripts/configure_services_auth.py
```

The setup script preserves existing credentials, generates missing ones, and
writes both plaintexts and hashes to the ignored local `.env` without printing
them. It also writes the private `secrets/<client-id>.env` files loaded by the
client containers. These contain `CLIENT_ID` and `CLIENT_SECRET` for Go clients,
plus `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET` and `OAUTH_TOKEN_URL` for .NET clients
and the gateway. `OAUTH_TOKEN_URL` serves only the clients that still request their
token through the gateway.

## Signing Key

The setup script generates or reuses an RSA private key at
`JWT_PRIVATE_KEY_FILE` (default `./secrets/jwt-private.pem`). Only User Management
mounts it at `JWT_PRIVATE_KEY_PATH=/run/secrets/jwt-private.pem`. `JWT_KEY_ID`
identifies its public key. The committed template contains a file path, never PEM
key material. A PEM file can also be generated manually with:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out secrets/jwt-private.pem
```

The issuer loads client hashes from the mounted `config/service-clients.yaml`.
Clients on the message broker request their tokens with a `Send` to
`user-management`, operation `POST /api/v1/oauth2/token`, using form-body client
credentials; it is the only operation the broker accepts without a token. Clients
not yet on the broker use `GATEWAY_URL/user-management/api/v1/oauth2/token`. They
cache tokens and refresh them before expiry; callers never sign tokens locally.

## Map and Monster Raid

Map and Monster Raid send every call to another service and every event through
the broker. Each peer has a transport switch, `grpc` by default: Map's
`USER_MANAGEMENT_TRANSPORT`, and Monster Raid's `GUILD_TRANSPORT`,
`PACKAGE_REGISTRY_TRANSPORT` and `TAMAGOTCHI_TRANSPORT`. Compose sets `rest` for
every peer whose pinned image serves no gRPC yet, so the call goes out as the REST
operation over `Broker.Send`; the line is removed when that peer's gRPC release is
pinned. Monster Raid makes no call to User Management: rewards travel in
`raid.completed.v1`.

Both export traces and metrics over OTLP to `OTEL_EXPORTER_OTLP_ENDPOINT`, whose
default `http://otel-collector:4317` is the stack's collector, so Compose does not
set it. `OTEL_SDK_DISABLED=true` turns their telemetry off.

## Guild and Package Registry

Guild and Package Registry load only their own `secrets/<client-id>.env` file,
not the shared `.env`. Both accept the generated `OAUTH_CLIENT_ID` and
`OAUTH_CLIENT_SECRET` aliases. Compose maps other required settings explicitly.
Their REST APIs and databases have no published host ports. Only Guild's separate
WebSocket listeners are published, at ports 8081 and 8083 by default. Each instance
has its own public address; use the URL returned by negotiation. Set
`GUILD_PUBLIC_WS_URL_1` and `GUILD_PUBLIC_WS_URL_2` to client-reachable `ws://` or
`wss://` base URLs when clients use another host.

Both services use `REQUEST_TIMEOUT_SECONDS: 4` in Compose, below the gateway's
default `5s` upstream timeout. Their per-instance `MAX_CONCURRENCY` limits default
to 64; timed-out work retains its slot until
it stops. `PACKAGE_REGISTRY_ADMIN_USER_IDS` is a comma-separated allowlist of
existing UMS user UUIDs. An empty value grants no administrator access.

Guild runs as `guild-api-1` and `guild-api-2`, sharing PostgreSQL messages, tickets
and presence. LISTEN/NOTIFY delivers chat across instances, and broadcasts check
current membership. Package Registry uses `deploy.replicas: 2` and a shared
PostgreSQL database. Both services serialize startup migrations, register their
REST listener with Discovery, and expose `/health` and `/status` internally. The
broker routes to both Guild instances from the Discovery catalogue.

## Storage and Rotation

Keep `.env` and `secrets/` outside Git. Back them up in encrypted storage or a
password manager. Share each client credential only with its service owner; keep
the issuer's private key with the deployment operator. The private directory uses
mode 700 and credential files mode 600. The key file is readable by the non-root
container inside that private host directory.

For secret rotation, add the new hash alongside the old one in the issuer's
registry, restart the issuer, update the corresponding client secret, recreate
that service, and remove the old hash. Update the matching `.env` plaintext before running the setup script;
it synchronizes the client's private file and issuer hash. During signing-key rotation, publish both public keys until old tokens
expire. Never distribute private keys as public rotation material.

If Docker on macOS cannot read a cloud-offloaded key, rerun the setup script.
It materializes the existing key without generating a replacement.

## First account on a clean deployment

After `python3 scripts/configure_services_auth.py` and `docker compose up -d --wait`, run `1. Setup and Authentication` and `1b. Package Bootstrap` in the User Management Postman collection. Registration omits `initialPackageId`; the resulting user can log in, create a package, activate it as its developer, then join it through User Management. All requests use the gateway. No package seed, SQL insert or change to Package Registry authorization is required.

The UMS migration permits a null initial package and preserves existing accounts and memberships. A supplied initial package must still be ACTIVE. Package Registry administrator configuration for raid operations is a separate concern.
